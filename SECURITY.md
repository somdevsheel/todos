# Security

This summarizes what's actually implemented today. Deep detail on the auth-specific items lives in [AUTHENTICATION.md](./AUTHENTICATION.md) — this file is the checklist view across the whole system.

## Implemented

- **Transport**: `helmet()` on every API response; the web app sets its own baseline headers (`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`) via `next.config.mjs`, since `helmet()` only covers the API's JSON responses, not the actual pages a browser renders. CORS locked to an explicit origin allowlist (`CORS_ORIGINS`), not a wildcard — the browser never calls the NestJS API directly except the WebSocket gateway (a deliberate, documented exception — see AUTHENTICATION.md).
- **Passwords**: Argon2id, explicit cost parameters, never logged, never returned in any API response. Every password field is bounded 8-128 characters (`IsStrongPassword()`/`LoginDto`) — the upper bound exists specifically so an unbounded string can't reach `argon2.verify()` on the public, rate-limited `/auth/login` endpoint (Argon2's cost scales with input size on top of its configured memory/time cost; OWASP's password-storage guidance calls this out explicitly).
- **Tokens**: JWT access tokens (short-lived) + opaque, hashed, rotating refresh tokens with reuse detection — presenting an already-rotated refresh token revokes every session for that user, not just the one being reused (see [AUTHENTICATION.md](./AUTHENTICATION.md)). Invitation tokens, password-reset tokens, and WebSocket connection tickets are hashed/stored the same way; the WS ticket is additionally single-use (atomic Redis `GETDEL`) and 30s-lived.
- **RBAC**: enforced server-side via a three-guard pipeline (`JwtAuthGuard` → `RolesGuard` → `OrgScopeGuard`) applied globally (`APP_GUARD`), not per-controller — a new module is authenticated-by-default even if nobody remembers to add a guard to it. Role assignment (including granting `SUPER_ADMIN`) is itself `SUPER_ADMIN`-only, and a `SUPER_ADMIN` can never revoke their own last `SUPER_ADMIN` role — the org can't be locked out of having an admin.
- **Organization scoping ("never trust a frontend-supplied id")**: every `:id` route that resolves to a single resource is checked against the caller's `organizationId` by `OrgScopeGuard` before the handler runs (generic — works against any Prisma model's `organizationId` column via one decorator, no per-model guard code needed); every collection query is filtered by `organizationId` at the service layer, sourced from the verified JWT, never from a request parameter. Chat (`Conversation`/`Message`) deliberately uses a *stricter* same-conversation-membership check instead of the generic guard — not-a-member is reported identically to not-found, hiding a conversation's existence from fellow-org employees who simply aren't in it, not just from other organizations.
- **Input validation**: every request body is a `class-validator` DTO with `whitelist: true, forbidNonWhitelisted: true` — unknown fields are rejected, not silently dropped. Every free-text field (titles, descriptions, names, comment/message bodies) carries an explicit `@MaxLength()` — closes an unbounded-storage-growth vector where any authenticated user, including the lowest-privilege role, could otherwise post arbitrarily large content on every request up to Express's body-size ceiling.
- **Email HTML injection**: invitation and password-reset emails interpolate user-controlled profile fields (`firstName`/`lastName`, an org's `name`) directly into a raw HTML string — unlike the React web app, there's no framework-level auto-escaping for that. Both templates escape those values before interpolation (`escapeHtml()`), since `invitedByName` in particular lands in a *third party's* inbox (the invitee), making it a real HTML-injection vector, not just a self-XSS one.
- **File uploads**: MIME-type allowlist and a configurable size cap (`FilesService.upload`), enforced against the real bytes server-side, not just trusted from the client; a hard multer-layer ceiling (25MB) rejects an oversized upload before it's fully buffered in memory. The on-disk storage key is always a server-generated UUID, never derived from the client's filename — sidesteps path traversal and filename collisions entirely, checked again as defense-in-depth inside `LocalDiskStorageProvider`.
- **Rate limiting**: a global default throttle (`@nestjs/throttler`, configured from `THROTTLE_TTL`/`THROTTLE_LIMIT`) plus a stricter explicit limit (5 requests/minute) on every unauthenticated auth-adjacent endpoint (login, accept-invitation, forgot-password, reset-password, refresh).
- **No user enumeration**: login failures for "no such account," "wrong password," and "domain not allowed" all return the identical generic message; the account-inactive check only runs *after* password verification succeeds, so it can't be used to probe whether an email exists without already knowing its password. `forgot-password` returns the identical response whether or not the email exists.
- **Error handling**: a single global exception filter produces the `{success:false,error:{code,message}}` envelope for every error path; unexpected exceptions are logged in full server-side (with stack trace) but the client only ever receives a generic message — a raw stack trace never crosses the wire, in any environment, not just production.
- **Company-domain restriction**: centralized in one service (`EmailDomainService`), backend-enforced at every account-creation/authentication touchpoint — see [AUTHENTICATION.md](./AUTHENTICATION.md).
- **Config fail-fast**: a zod schema validates every environment variable at bootstrap; production mode additionally requires ≥32-character JWT secrets, a non-localhost CORS origin, and a real SMTP host (not the dev MailHog catcher) — misconfiguration aborts startup instead of surfacing later as a runtime security gap.
- **Audit logging**: every invite, reinvite, activation, login (success and failure, with a reason), logout, logout-all, password-reset request/completion, role assignment/revocation/permission-edit, and CRUD mutation on departments/teams/organization settings/announcements writes an immutable `AuditLog` row with actor, IP, user agent, and a JSON metadata blob. Audit-log write failures are caught and logged, never allowed to fail the business operation they're describing (see `AuditService.log()`), and never permanently lost by design (no delete endpoint exists).
- **Secrets**: `.env` is gitignored (confirmed never committed, in any commit, across this repo's history — not just "should be"); `.env.example` contains no real values; the JWT/SMTP/database secrets used locally are dev-only placeholders documented as such. `pnpm audit` shows no vulnerabilities in any dependency actually reachable at runtime by an attacker — the few findings that exist are all deep inside build-time tooling (Expo/Metro's bundler chain, Prisma's CLI config resolver, Firebase Admin's GCS client chain), not application code paths.

## Deliberately not built yet

- **CSRF tokens as a separate mechanism** — covered today by `SameSite=Lax` cookies plus the BFF-only architecture (the API's CORS policy rejects everything except the Next.js origin); a dedicated CSRF token would be revisited if the cookie policy ever needs to loosen.
- **Content-Security-Policy** — the web app ships the other baseline headers (frame/content-type/referrer/permissions) but not a CSP yet; this app's actual script/style/connect sources (Next.js hydration, the direct browser→API WebSocket connection) need to be enumerated and tested against a real build before a policy ships, rather than guessing one that silently breaks something. Real follow-up, not a silent gap.
- **Fine-grained permission-key authorization** — Phase 7 built a real editing API/UI for `Permission`/`RolePermission` (`PATCH /roles/:id/permissions`), but no guard consults that data yet; every authorization check in the app is still role-name-based (`@Roles('ADMIN')`). Editing a role's permissions today persists real, audited data but doesn't change what any endpoint allows — stated plainly in the UI copy, not just here.
- **MFA / SSO** — not in the current roadmap (see [ARCHITECTURE.md](./ARCHITECTURE.md)).
- **Production TLS termination, NGINX security headers, firewall rules** — nothing is deployed yet; see [DEPLOYMENT.md](./DEPLOYMENT.md) and [LIGHTSAIL.md](./LIGHTSAIL.md).

## Known, low-severity, accepted

- **Conversation removal's creator-privilege doesn't re-check current membership** — a user who creates a group conversation, then later removes themselves from it, permanently keeps the ability to remove *other* members from a conversation they're no longer part of (they still can't read it, or add anyone back). Narrow, self-inflicted, low-impact; not fixed pre-deployment, but worth knowing about.

## Reporting

There is no external-facing deployment yet, so there is no public security-contact process to document. Internally, security-relevant findings should be raised directly with the workspace's SUPER_ADMIN.
