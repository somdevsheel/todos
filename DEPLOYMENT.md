- [x] **Install NGINX + certbot**, deploy `docker/nginx/api.arutechconsultancy.com.conf.template` (fixed a real version-compat bug along the way — `http2 on;` as a standalone directive only works on NGINX 1.25.1+, but Ubuntu 22.04's `apt` package ships 1.18.0; switched to the portable `listen 443 ssl http2;` combined syntax), issued a real Let's Encrypt cert via `certbot certonly --standalone`.

Also hit and fixed a real Lightsail-console firewall gap along the way (its network firewall defaults to SSH-only; had to explicitly add HTTP/HTTPS rules — separate from the OS's own `ufw`). **The backend is genuinely live.**
- [x] **Vercel**: project created, connected to this repo, env vars set, `workspace.arutechconsultancy.com` attached. Done — with two real bugs found and fixed along the way:
  1. **Monorepo build gap**: Vercel's default Build Command only ran `apps/web`'s own `next build`, never building the sibling `packages/shared-types` workspace package first — ~20 files failed with `Module not found: Can't resolve '@arutech/shared-types'`. Fixed with an explicit Build Command override: `cd ../.. && pnpm --filter @arutech/shared-types build && pnpm --filter @arutech/web build` (see [VERCEL.md](./VERCEL.md)).
  2. **A real, significant `apiFetch` bug**: `logout`/`logout-all`/`forgot-password`/`reset-password` all return `204 No Content` on success (no body, per HTTP spec) — but `apps/web/src/lib/api-client.ts`'s `apiFetch()` unconditionally tried to `.json()`-parse every response, silently treating the resulting parse failure as a null body, which was then treated as an *error* — so a **genuinely successful password reset was being reported as a failure**, and the wrapped error response (attempting a body on a 204) then threw a real 500 in the BFF route. Confirmed live: the backend had actually already changed the password correctly on the very first attempt, every time — only the frontend's error handling was wrong. Fixed in `apiFetch()` (special-cases `res.status === 204` before attempting to parse), with 4 new regression tests. **The full stack is confirmed working end to end** — real login on `https://workspace.arutechconsultancy.com`, real session, real Postgres-backed data.

## Target architecture

See the diagram in [ARCHITECTURE.md](./ARCHITECTURE.md). Summary: `apps/web` deploys to Vercel ([VERCEL.md](./VERCEL.md)); `apps/api` deploys as a single Docker container on the existing AWS Lightsail instance, behind NGINX, alongside — not replacing — whatever else already runs there ([LIGHTSAIL.md](./LIGHTSAIL.md)).

**One container, not three.** The original roadmap named `workspace-worker`/`workspace-websocket` as separate containers; ARCHITECTURE.md's "Phase 8: a named deviation" section explains why that's the wrong call today (short version: `PresenceService` is in-process-only, so splitting the WebSocket gateway out would break presence; the reminder worker has two independent idempotency layers and doesn't need a split to be safe). What ships is one `arutech-workspace-api` container running REST + WebSocket gateway + BullMQ scheduler/processor — exactly how it already runs in dev.

## What's real and verified

- **`docker/api.Dockerfile`** — the production image. Built, booted in production mode against real dockerized Postgres/Redis, confirmed serving health traffic — this was true before Phase 8 and remains the foundation everything else builds on. Uses `node:20-bookworm-slim` (not alpine — `argon2`'s native addon doesn't reliably resolve prebuilds against musl libc), a dedicated `prod-deps` stage (see the Dockerfile's own comments for why `pnpm deploy --prod`/`pnpm prune --prod` were tried and rejected), runs as a non-root user.
- **`docker/docker-compose.prod.yml`** (new) — the production stack: `api` (loopback-only port 4000, so NGINX is the only way in), `postgres`/`redis` (no published ports at all — reachable only over the compose-internal network), a persistent named volume for uploads, `redis --appendonly yes` for durable BullMQ queue state, log rotation on every service. **Built, booted, and health-checked end-to-end in this environment** — real Postgres+Redis+API containers, `docker exec ... node_modules/.bin/prisma migrate deploy` applying all 4 real migrations, `GET /health` returning `{"status":"ok","database":"up","redis":"up"}` in actual `NODE_ENV=production` mode. Not simulated — this was the single biggest verification win of this phase.
  - **Deploy command note**: `docker compose exec api pnpm --filter @arutech/api prisma:deploy` does **not** work — the runtime image is deliberately slim (no pnpm/corepack, just `node`). The correct, verified command is `docker compose exec api node_modules/.bin/prisma migrate deploy` (documented directly in the compose file's header comment, found by actually running it, not assumed).
  - **`.env.production` footgun, worth knowing**: `POSTGRES_USER`/`PASSWORD`/`DB` (read natively by the postgres image) and `DATABASE_URL` (read by the api container) must agree — nothing enforces that automatically. Get them out of sync and Postgres boots fine while the API can't connect to it.
- **`.env.production.example`** (new) — a production-shaped template, distinct from `.env.example` (which is tuned for local dev — MailHog, permissive secrets, localhost CORS). `.gitignore` was fixed alongside this: `.env.production` wasn't actually covered by the old `.env.*.local` pattern before this phase — a real gap, now closed.
- **`apps/api/src/files/storage/s3.storage.ts`** (new) — a real `S3StorageProvider`, works against AWS S3 or any S3-compatible endpoint (MinIO, DigitalOcean Spaces). Tested against a mocked `@aws-sdk/client-s3` the same way `FcmService` is tested against a mocked Firebase Admin SDK — no real bucket exists in this environment, same honesty precedent. Fails loudly at construction if selected without complete config, unlike FCM's graceful-degradation pattern — a misconfigured file-storage backend has no sensible degraded mode. `STORAGE_REGION` matters for real AWS S3 specifically (used in request signing) even though most S3-compatible servers ignore it — logs a clear warning, not silence, when left unset. **`STORAGE_PROVIDER=local` stays the shipped default** — see "Known production gap: file storage" below for why that's still the right call, not a shortfall.
- **`docker/nginx/api.arutechconsultancy.com.conf.template`** (new) — a complete NGINX server block: HTTPS + HTTP→HTTPS redirect, WebSocket upgrade headers on the same location block that serves REST (both hit the same `127.0.0.1:4000` upstream), baseline security headers matching `apps/web/next.config.mjs`'s, `client_max_body_size 26m` (a hair above multer's *hard* 25MB ceiling — the real binding constraint, not the softer configurable `MAX_UPLOAD_SIZE_MB`). Explicitly marked as a template — per [LIGHTSAIL.md](./LIGHTSAIL.md), not to be applied before that checklist is walked against the real host's existing config.
- **`.github/workflows/ci.yml`** (new) — genuinely runs on every push/PR, no cloud credentials needed: build+lint+test (no service containers required — every unit spec mocks Prisma), a full e2e job against real Postgres+Redis+MailHog service containers, and a Docker build-only job. This is real, verifiable CI, not aspirational.
- **`.github/workflows/deploy.yml`** (new) — `workflow_dispatch`-only (no auto-deploy on push), SSH-based `git pull && docker compose build && up -d && migrate deploy` on the target host. **Syntactically ready, has never successfully run** — needs `LIGHTSAIL_HOST`/`LIGHTSAIL_USER`/`LIGHTSAIL_SSH_KEY` secrets that don't exist. Auto-deploying to a shared host this repo has never inspected would be inappropriate regardless — manual trigger is correct until `LIGHTSAIL.md`'s checklist is actually walked.
- **`scripts/backup-postgres.sh` / `scripts/restore-postgres.sh`** — see [BACKUPS.md](./BACKUPS.md). Run for real, end-to-end, against the live dev database this session: backed up, restored into a genuine scratch database, every one of 29 tables' row counts verified identical via real `COUNT(*)` queries (not the stale `pg_stat_user_tables` estimate, which was tried first and gave misleadingly different numbers).
- **Structured logging: deliberately not adopted.** Every service already uses NestJS's default `Logger` consistently; Docker's own log capture plus `docker-compose.prod.yml`'s log-rotation block is sufficient for a single-instance deployment with no log-aggregation pipeline planned. Migrating to `pino`/`nestjs-pino` would touch dozens of call sites for a structured-JSON benefit that only pays off once something actually consumes it — revisit if/when log search across multiple people or multiple instances becomes a real operational need, not before.

## Known production gap: file storage

`STORAGE_PROVIDER=local` writes uploaded files to a directory on the API container's own disk — a named volume in `docker-compose.prod.yml`, so it survives a container restart/redeploy. This remains fine for exactly the single-instance topology this phase deliberately ships (see ARCHITECTURE.md's "Phase 8: a named deviation" — there's no second API replica for uploads to go missing from). It breaks the moment there's ever more than one API instance, at which point `STORAGE_PROVIDER=s3` (real, tested code, just needs real bucket credentials) is the fix, not a rewrite.
