# Chat

**Status: done.** Conversations, messages, a Socket.IO gateway, typing indicators, presence, read receipts, and @mentions are all real and verified live (see "Verification" below).

## What exists today

- `Conversation` (DIRECT/GROUP), `ConversationMember` (`lastReadAt` drives unread counts), `Message` (soft-deletable, editable, `mentionedUserIds` — added in migration `message_mentions`, mirroring `TaskComment.mentionedUserIds`), `MessageAttachment` (schema exists; attachment upload isn't wired to chat yet — see "Known simplifications").
- REST: `POST/GET /conversations`, `GET /conversations/:id`, `PATCH /conversations/:id/read`, `POST/DELETE /conversations/:id/members(/:userId)`, and nested `GET/POST /conversations/:id/messages`, `PATCH/DELETE /conversations/:id/messages/:messageId` — see `apps/api/src/conversations/`, `apps/api/src/messages/`.
- An authenticated Socket.IO gateway at `apps/api/src/websocket/` (`ChatGateway`). Auth happens once per connection, in a `server.use()` middleware (not the `OnGatewayConnection` lifecycle hook — an earlier version of this gateway had a real race there: a client could emit an event immediately on `'connect'` before the server's async ticket-verification/room-join had actually finished, and it would silently no-op. Socket.IO doesn't fire `'connect'` on the client until every `server.use()` middleware resolves, so moving that work there closes the window entirely) — see AUTHENTICATION.md's "WebSocket authentication" section for the full ticket-based auth flow.
- Events: `message:new`/`message:updated`/`message:deleted` (server → client, broadcast to a `conversation:<id>` Socket.IO room every member is auto-joined to on connect), `typing:start`/`typing:stop` (client → server → relayed to the room, never persisted), `conversation:focus`/`conversation:blur` (client → server; drives both the read-receipt and the notification-dedup rule below), `presence:online`/`presence:offline` (server → the conversations that user shares with others, on the first-connect/last-disconnect transition only) and `presence:snapshot` (server → the connecting client only, once, so a freshly opened chat UI isn't blind until the next transition happens to fire).
- Read receipts via `ConversationMember.lastReadAt` — never a separately-maintained unread counter. Bumped both by the explicit `PATCH .../read` endpoint and by `conversation:focus`, **and** kept current for every message that streams in while a member is actively focused (not just at the moment they first opened the thread) — see `MessagesService.notifyRecipients` and `ConversationsService.markReadForUser`.
- @mentions: an explicit picker (`mentionedUserIds`, populated by the same `AssigneePicker` component task comments already use), not parsed from message text — see the field's docstring in `schema.prisma` for why that choice was made consistently with `TaskComment`.
- Online/push notification dedup, exactly as originally planned here: a conversation member currently focused on that exact conversation gets the message live over the socket and nothing else — no `Notification` row, no push. Everyone else gets the normal pipeline (`NEW_MESSAGE`, or `MESSAGE_MENTION` if they were @mentioned), respecting their `NotificationPreference` (Phase 4) like every other notification type. See `MessagesService.notifyRecipients`.
- A full web chat UI (`apps/web/src/app/(dashboard)/chat/`, `components/chat/`): a live-updating conversation list (unread badges, last-message preview, presence dots), a conversation view with real-time message delivery, a typing indicator, and a composer with mention support. The socket connection is scoped to the `/chat` route tree (`SocketProvider`, mounted in `chat/layout.tsx`) — not a global always-on connection for the whole app in this phase.

## Known simplifications

- **No auto-provisioned org-wide default channel.** The spec's `#general`-style "organization-wide default membership handled at creation time" isn't built — creating a company-wide channel today means creating a GROUP conversation and adding every employee explicitly, the same manual process as any other group.
- **Presence/typing/focus state is in-process** (a plain `Map` in `PresenceService`), not Redis-backed — matches the single-instance topology this app actually runs on (see DEPLOYMENT.md/ARCHITECTURE.md), same reasoning as the Phase 3 reminder worker staying in-process. Horizontal scaling would need this fanned out via Redis pub/sub.
- **A member removed from a conversation while connected keeps that Socket.IO room until their next reconnect** — there's no cross-module broadcast-eviction wired up for the rare "kicked mid-session" case.
- **Message attachments aren't wired up** — `MessageAttachment`/`File` can theoretically be linked, but there's no upload UI or endpoint for chat specifically yet (Task attachments, a separate feature, do work — see ARCHITECTURE.md's Phase 2 entry).

## Verification

Live-verified against the real API + Postgres + Redis (not just unit tests): two authenticated Socket.IO connections (via `socket.io-client`, using real ws-tickets minted through the actual `/auth/ws-ticket` flow), a REST-created message landing over `message:new` in real time, the focused-recipient dedup rule (no `Notification` row created, `lastReadAt` kept current while watching live), and the non-focused case (a real `Notification` row created) — all confirmed against live server behavior. This live pass is also what caught and fixed the `server.use()` middleware race described above and the streaming-unread-drift bug, neither of which the unit tests (which mock `PresenceService`/Prisma) would have caught on their own.
